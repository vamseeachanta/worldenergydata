## Verdict

## Findings

**MAJOR-1 — Issue-mandated "virgin-pressure proxy" deliverable is missing entirely.**
Issue #725 Output spec: *"…the #709 schema (…) — **earliest observation per well flagged as the virgin-pressure proxy**."* The plan's curated schema (lines 114–119) has no earliest-per-well flag, and no task (Task 4, lines 361–382) computes one. Searching the plan for "virgin" / "earliest" returns nothing. This is not incidental — the parent epic (#708) is an *under-pressured / virgin-pressure* screen; #710 needs the earliest annual SHUT_IN_PRESS per well to establish the virgin baseline. A per-well `min(test_year)` flag is trivially supportable from the `YEAR` column, so "where the Kansas data can support it" (line 112) does not excuse the omission. **This alone blocks acceptance against the issue's own criteria.**

**MAJOR-2 — psig→psia unit handling is unaddressed; schema column is `pressure_psia` but KGS SHUT_IN_PRESS is gauge.**
The curated field is `pressure_psia` (absolute), and the plan maps `SHUT_IN_PRESS` straight into it (line 124, pseudocode line 271). KGS proration shut-in pressures are reported as gauge (psig). At the low pressures this dataset actually contains — the live sample shows `SHUT_IN_PRESS=47.3` (line 62) — the ~14.7 psi gauge/absolute offset is a **~31% error**. Repo rule 1 in `CLAUDE.md` explicitly mandates standardized units. The plan must either (a) convert psig→psia and document the atmospheric constant, or (b) rename/redocument the column as gauge with an explicit flag. As written it will emit wrong-by-a-third "absolute" pressures.

**MAJOR-3 — Ambiguous api10→api14 joins null `api14` but the plan never suppresses the depth-derived gradient.**
The plan correctly fails soft on ambiguous joins by nulling `api14` and flagging (lines 130–132, 372–373). But the gradient denominator `reference_depth_ft` also comes from the wells-master join (`ks_wells.DEPTH`, lines 126, 272). On a one-to-many api10 join (sidetracks/recompletions sharing an API-10 base with different `API_NUM_NODASH` and different DEPTHs), the plan says nothing about which DEPTH is used or whether the gradient is suppressed. The gradient-guard tests (lines 366–367, 456) only check *positive depth*, not *join uniqueness*. Result: a row can carry `api14=null` (correctly flagged ambiguous) yet still publish a `gradient_psi_ft` computed from an arbitrarily-picked well's depth. Gradient must be suppressed/flagged whenever the depth source is ambiguous, and a test must assert it.

**MODERATE-4 — The county-code→FIPS assumption is baked into a passing test without empirical verification.**
Test `test_api_county_code_maps_to_county_name` asserts `15-067-20048 → county_name=Grant` (lines 452, 293). This is only correct if Kansas API county codes equal FIPS codes (Grant KS = FIPS 067). Many states use a state-specific *sequential* API county code that is **not** FIPS; if KGS does, `067` is not Grant and both the county map and the issue's "Hugoton counties dominant" sanity check (line 372, issue AC) are wrong. The PLSS in the sample (Township 29S, Range 37W — the far-SW tier) is *consistent* with Grant, which is reassuring, but the plan should verify the scheme empirically (join a handful of known wells / cross-check township-range) rather than assert FIPS in a green test. Note also `kansas_counties.yml` must cover all 105 counties, not just the sampled one.

**MODERATE-5 — Task 1 omits the setuptools packaging config required to actually ship the YAML data.**
The package ships two data files (`source_catalog.yml`, `kansas_counties.yml`, lines 168–169) and the code loads them as package data (pseudocode line 226). The sibling pattern (`texas_rrc/pyproject.toml`) needs an explicit `[tool.setuptools.packages.find]` with `include = ["worldenergydata.texas_rrc*"]`, `namespaces = true`, **and** a `[tool.setuptools.package-data]` glob for `**/*.yml`. Task 1 (lines 296–301) mentions only the dependency set and `[tool.uv.sources]`. Omitting the find-include + package-data means the YAML won't be packaged (and risks setuptools discovering a bare `worldenergydata` regular package, colliding with the namespace root). Add this to Task 1 explicitly.

**MODERATE-6 — `test_type` constant and `test_date` provenance for annual proration rows are unspecified.**
Issue #709/#725 schema pins `test_type=KS_PRORATION`; the plan lists the field (line 116) but never states the constant value. More importantly, the proration file has only an annual `YEAR` — there is **no test date column**. The curated schema requires `test_date` (line 115), yet the plan's date-parsing discussion (lines 141–142, Task 3) refers only to `ks_wells.txt` Oracle dates, not proration observation dates. The plan must state that proration `test_date` is null (or a documented year-derived value) and that ordering for the virgin-pressure flag relies on `test_year`.

**MINOR-7 — Header whitespace stripping is a real gotcha absent from the test list.**
The live header (line 59) has inconsistent spacing: `SHUT_IN_PRESS, WORKING_PRES,DAILY_RATE, … WATER_PROD,METER_PRES`. A default `csv.reader` yields column names with leading spaces (`" WORKING_PRES"`). The parser must strip header tokens; no test asserts this.

**MINOR-8 — "Skip exact malformed second line" is brittle.**
Pseudocode (line 245) and Task 3 (line 337) skip the *exact* fragment `RES","DIFFERENT","COEFF"`. Prefer positional skip (line index 1) or, more robustly, drop any row whose field count ≠ the 22-column header. An exact-string match silently fails if KGS reposts with a slightly different mangling.

**MINOR-9 — CLI registration touches four sites; the plan enumerates two.**
`main.py` requires both an entry in the `from worldenergydata.cli.commands import (…)` tuple **and** an `app.add_typer(kansas_kgs.app, name="kansas-kgs", …)` call; `commands/__init__.py` has **both** the `_COMMAND_MODULES` set and the `__all__` list. The plan (lines 396–397, Files-to-Change lines 435–436) says "register" / "add lazy allowlist entry" without enumerating all four edit points — an easy miss that will break the import.

**MINOR-10 — Dependency pins don't match repo convention.** Task 1 lists bare `pandas`, `pyarrow`, `pyyaml` (line 298); the sibling `texas_rrc` pins ranges (`pandas>=2.3.3,<3.0`, etc.) and `requires-python>=3.10`. Match the convention.

`★ Insight ─────────────────────────────────────`
- The most dangerous plan defects here aren't structural — the scaffolding claims all verified. They're *semantic*: a column named `_psia` fed gauge data, and a "gradient" that survives an ambiguous join. Adversarial plan review pays off most on the numbers a downstream consumer (#710) will trust blindly.
- "Follows the #709 schema where the data can support it" is a hedge that quietly dropped a hard issue deliverable (virgin-proxy flag). When a plan cites a schema, diff the plan's field list against *both* the schema and the issue's explicit outputs — omissions hide in the gap between them.
- WHP-over-total-depth is dimensionally psi/ft but physically not a fluid gradient; the plan flags it `screening_only`, which is the right instinct — but a flagged-yet-published misleading number still needs its computation gated (positive pressure **and** unambiguous depth), or the flag becomes the only thing standing between a screening artifact and a false "under-pressured" call.
