# Plan Review Artifact — Issue #342 — Codex

- Verdict: MAJOR
- Retrieval adequacy: adequate

Key findings
- The plan is not implementation-ready because it leaves the core boundary decision unresolved: restore the missing `cost.calibration.proxy_comparison` API or retarget the regression test. Those are materially different outcomes and the plan must choose one.
- The BSEE-side precedent is not a thin transplant path as written. `src/worldenergydata/bsee/analysis/cost/cost_calibration.py` uses a pandas/DataFrame + BSEE-model surface, while `src/worldenergydata/cost/calibration/cost_predictor.py` uses `CostDataPoint` objects; region/proxy keys also differ from the sanctioned dataset (`gom`/`north_sea`/etc. vs `GOM`/`NCS`/`UKCS`/`West Africa`/`Asia-Pacific`).
- The TDD list does not preserve the actual regression contract already expressed in `tests/unit/cost/test_proxy_comparison.py` (non-empty output, positive rates, multi-region coverage, required fields, dataclass behavior, bias sign semantics).
- Acceptance criteria are partly qualitative and not executable enough to gate implementation.

Main blockers to fix
1. Choose and lock one boundary strategy: restore `src/worldenergydata/cost/calibration/proxy_comparison.py` as the supported API, or explicitly retire it and retarget all callers/tests.
2. If restoring the module, specify the adapter contract in detail: input types, region-name normalization, reuse vs duplication of BSEE models, and how `CostPredictor` outputs become day-rate comparisons without inventing a second unsupported API.
3. Rewrite the TDD and acceptance sections so they preserve the concrete assertions already present in `tests/unit/cost/test_proxy_comparison.py` and make compatibility expectations executable rather than qualitative.
