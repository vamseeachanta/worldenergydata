Big Foot manifest-lineage hotfix design

Issue: worldenergydata #1039
Follow-on: worldenergydata #1048
Design approval: user-approved 2026-07-18; written-spec approval remains pending.

Problem

Manifest v1 records feature commit 80b6560a947af49057dd4bbc7364b88ad8867db3 as its producer. PR #1049 was squash-merged to main as 66ce9d6808492a01f6a7cac60415304bcc6e6ef5. The feature commit is not an ancestor of the durable main lineage, so a clean depth-one checkout cannot satisfy the existing producer-ancestry contract. The checked-output regeneration test consequently fails on Python 3.10, 3.11, and 3.12.

The previous main run already contained unrelated capability-index, logging, repository-structure, workflow-API, and Python 3.10 compatibility failures. This design will address only the new cost-specific producer-lineage regression.

Decision

The hotfix will preserve production's fail-closed Git commit and executable-blob validation. It will republish manifest v1 with durable producer commit 66ce9d6808492a01f6a7cac60415304bcc6e6ef5, whose executable blobs match the published evidence pack and which remains an ancestor of subsequent main commits.

Alternatives considered

ApproachDispositionReason
Pin the durable squash commit and add a squash-lineage regression.SelectedRepairs the published manifest without weakening provenance or changing production code.
Fetch the orphaned feature SHA and relax the ancestry check.RejectedWould convert repository provenance into acceptance of an unreachable caller-selected commit.
Change the repository to merge commits.RejectedWould be systemic, would not repair the existing manifest, and belongs outside this hotfix.

Change boundary

The implementation will modify only:

  • tests/unit/cost/test_big_foot_cost_lineage.py, a focused lineage regression file that will model a squash merge, branch deletion, durable-producer success, and real-Git rejection attacks without exceeding the existing hardening file's 400-line limit;
  • data/modules/cost/curated/cost_map_contract_manifest.v1.json, to record the durable producer commit and refreshed canonical manifest hash state if regeneration requires it.

The implementation will not modify production helpers, curated accounting rows, HTML or CSV semantics, source workbooks, workbook metadata, email state, or external-circulation policy. If deterministic regeneration shows that HTML or CSV bytes would change, the hotfix will stop and return to plan review.

Data and trust flow

  1. The test harness will resolve the artifact commit from the current checkout.
  2. For a shallow checkout, it will hydrate history only from configured origin.
  3. The manifest producer will have to exist as a real Git commit and be an ancestor of the artifact commit.
  4. Production validation will compare every executable input byte-for-byte with the producer's Git blobs.
  5. The builder will regenerate HTML, CSV, and manifest bytes; checked artifacts will have to match exactly.

Test design

The existing failing checked-output regeneration test will provide the initial RED evidence from the post-merge main run. A focused regression will then construct a complete local origin with:

  1. a durable base commit containing the executable inputs;
  2. a feature branch with an artifact commit;
  3. a squash commit on the default branch;
  4. the feature branch deleted before a depth-one clone;
  5. the durable base commit used as producer.

The regression will require history hydration, ancestry validation, and byte-identical regeneration to pass. It will also retain rejection coverage for fabricated producers, missing origin, dirty executable inputs, and non-ancestor producer commits.

Acceptance criteria

  • The checked-in manifest producer will be a real ancestor of the current durable main lineage.
  • A depth-one main-like checkout will regenerate the checked HTML, CSV, and manifest byte-identically.
  • The existing production validation API and fail-closed behavior will remain unchanged.
  • The three source workbook SHA-256 values will remain unchanged.
  • The focused cost tests, formatting, lint, legal scan, and adversarial review will pass.
  • The PR will use Refs #1039; #1039 will close only after merge verification.
  • No email, external circulation, workbook mutation, or unrelated full-suite debt remediation will occur.

Generalized follow-on

Issue #1048 will retain the broader design question: how deterministic manifests should identify producers across squash, rebase, shallow checkout, and branch-deletion workflows. This hotfix will not pre-empt that systemic contract.
