1 Executive Summary

The field development module is a deterministic offshore concept-screening and schematic tool. Analysis is performed to determine a concept shortlist and its schematic outputs; key results are summarized below.

  • The public near-host example is ranked as a subsea tieback.
    • A preference of 78.9 points is returned for a host distance of 18 km. The configured distance exclusion is 200 km; no engineering acceptance threshold is defined for the preference score. Example; scoring basis.
    • The returned architecture contains 6 nodes and 9 directed connections. These counts establish schematic connectivity, with no pressure, thermal, structural or capacity acceptance implied. Architecture basis.
  • A concept shortlist is available for engineering discussion.
    • Engineering selection is withheld until host capacity, fluid properties, route data and preference settings are supplied and assessed. The boundaries used here are ASSUMED - to be confirmed. Basis; recommendations.

2 Introduction

The offshore screening workflow is examined from concept input to ranked alternatives and schematic output. A synthetic example already published in the repository is used; no operating development or installation is represented. Example record; module scope.

The main workflow is covered in full for the stated input set. A documented public class, public functions and existing tests are present, so a worked calculation is presented rather than a readiness-only assessment. Public entry points; test evidence.

Not covered

Catalog joins, analog matching, historical calibration, terrain acquisition, production economics, equipment geometry, installation suitability, optimized routing and text-assisted concept completion are outside this calculation. Their availability in the package does not establish their qualification for engineering selection. Interface inventory; calibration limits.

3 Workflow, inputs and outputs

Field data are represented by the public concept model, and single-field validation is followed by cross-field checks. Ranking and schematic generation are separate calls; a ranked result is explicitly transferred into a concept before the drawings are generated. Input contract; ranking; rendering.

The reader supplies depth in metres, distance in kilometres, reserves in million barrels of oil equivalent, integer well counts and an explicit host-capacity statement. Only a name is mandatory in the model, so a successfully constructed sparse object is not a complete design basis. Model fields and checks.

The outputs are a descending concept shortlist with criterion scores, rationale and warnings; cross-field violation records; a graph of typed equipment and connections; and vector schematics. The drawing coordinates are synthetic. The example input register and all ranked outputs are given in the appendix. Ranking contract; schematic contract.

4 Basis and criteria

The calculation basis is restricted to the public near-host example and the repository's default screening configuration. The weighted-average method is supported by the cited manual; the chosen preference weights and field-development boundaries are assumptions, with no physical acceptance inferred from that manual. Method source; configuration source.

The example water depth is 1,400 m, recoverable reserves are 20 million barrels of oil equivalent and host spare capacity is explicitly present. A well count of 3 is supplied. These are synthetic inputs, not measurements. Public example.

The configured warning distance is 32 km, the attractiveness boundary is 60 km and the tieback exclusion distance is 200 km. The marginal-reserve boundary is 50 million barrels of oil equivalent. Each default is ASSUMED - to be confirmed; these values are screening settings rather than hydraulic or thermal operating limits. Threshold definitions.

A positive weight sum and consistently oriented criterion scales are required for interpretation of the weighted average. Mutual preference independence is required by the cited method and has not been established for the repository profiles. Host-capacity feasibility remains a supplied statement. Method conditions; implementation.

5 Theory and methodology

Candidate concepts are filtered by configured depth envelopes and host reachability, then ordered by a normalized weighted sum. Preference scores are used for comparison within this configuration; they are neither probabilities nor financial returns. Filtering and scoring.

Sᵢ = Σⱼ(wⱼ sᵢⱼ) / Σⱼwⱼ

Here Sᵢ is the normalized preference for candidate i, sᵢⱼ is its dimensionless score on criterion j, and wⱼ is that criterion's dimensionless weight. The appendix provides the weights and leading candidate scores at their calculation precision. The displayed preference in points is the normalized value expressed on a percentage scale, without a probability interpretation. January 2009 manual, overall weighted scores; module implementation.

Graph connectivity is assembled by routing each wet tree through a manifold to the host, with control connections in the opposite direction and a separate export connection. This is architecture bookkeeping rather than a pipe-network solution. Connectivity rules.

X = s x; Y = −s y; D = s d

Here x and y are schematic coordinates in kilometres, positive north along y; X and Y are drawing coordinates in pixels; s is the presentation scale in pixels per kilometre; d is the axis-aligned host offset in kilometres; and D is its drawing separation in pixels. The sign reversal matches the downward drawing axis. Translation for the drawing margin does not change separation. Coordinate and transform standard; implemented mapping.

The chosen drawing scale is 50 pixels per kilometre, an explicit presentation input. The default well-ring radius is 0.5 km, ASSUMED - to be confirmed as a presentation convention. No well coordinates, route geometry, mesh or physical boundary conditions are solved. Drawing conventions.

6 Worked example

The public example is calculated by calling the concept validation, ranking, graph and rendering interfaces. The leading candidate's architecture and the supplied host distance are transferred into the selected concept, followed by another sanity check. Example; validation; architecture.

The module returns 7 ranked candidates. The leading subsea tieback preference is 78.9 points. The input and selected concept produce 0 and 0 cross-field findings respectively; missing engineering data remain unresolved. Ranking output; sanity rules.

The returned schematic contains 3 subsea trees and 1 routing manifold, with 6 total nodes and 9 directed connections. The host-to-manifold drawing separation is 900 pixels at the stated scale. The manifold count is a drawing default, not an engineered equipment selection. Graph and scale output.

Logical production and control connections

Only host distance is changed in the sensitivity chart; depth, reserves, host-capacity statement, weights and all other example data are held fixed. The warning is applied above its boundary, attractiveness changes above its boundary, and exclusion is applied above the configured maximum. The line is drawn as steps because the calculation is heuristic. The zero-distance endpoint exposes ranking behavior only; a selected tieback without positive distance is rejected by the separate sanity gate. No engineering acceptance line is defined for preference points. Boundary comparisons.

7 Validation evidence

The repository's existing evidence is separated into input checks, heuristic behavior, connectivity, scale arithmetic and serialization. The appendix inventories the selected test functions; function counts are not executed-case counts because parametrization expands some tests. Evidence basis.

Existing tests check the expected near-host concept, ranking order, configuration overrides, tree-to-manifold connectivity, distance scaling, drawing structure and an extensible-markup round trip. These are software and arithmetic checks. A published measured benchmark for the public synthetic example is not supplied, and agreement with field performance is NOT_EVALUATED. Tests and qualification record.

Historical reference data and a calibration harness are present, but the depth priors were set using the same catalog evaluated by the harness. No held-out engineering prediction claim is made, and historical percentages are not reused as current results. Calibration disclosure.

The accompanying report tests contain hand-worked score, node-count, connection-count and distance-scale anchors. The remaining module-to-page comparisons are consistency checks, including every sensitivity point and every tagged displayed number. An exact document rebuild is checked only after numeric arrays and drawing coordinates have been rounded for presentation. Quality evidence.

8 Limits and recommendations

Use is limited to early concept discussion and schematic communication under explicit screening assumptions. Engineering acceptance remains NOT_EVALUATED for hydraulic behavior, thermal behavior, structural response, production capacity and economic selection. Calculation scope; evidence boundary.

Before selecting a tieback, obtain host capacity and receiving-condition data, fluid composition, operating rates and pressures, shutdown and restart requirements, route survey and governing acceptance criteria. Replace the assumed distance settings with criteria established by the appropriate flow, thermal, mechanical and commercial analyses; distance alone does not demonstrate operability. The repository's separate screening interfaces are not a substitute for those analyses. Supporting interface limitations.

Before relying on the ranking, agree the criterion scales and weights with the engineering decision team, test for overlapping preferences and perform sensitivity analysis. The cited manual identifies preference independence as a condition for additive scoring. Method conditions.

The recommended next evidence slice is a public, fully specified tieback benchmark with documented receiving conditions, independently calculated pressure and temperature results, and acceptance criteria. Ranking qualification is then assessed on a held-out catalog with explicit host data. Until that evidence is supplied, release remains restricted to screening and schematic use. Current gaps; holdout gap.

9.3 Quality evidence and rebuilding

The arithmetic anchors check the weighted score, node count, connection count and drawing separation against hand-worked literals. Absolute floating-point tolerance is stated in each test; counts are exact. The displayed criterion inputs are also recombined to the displayed headline precision. No solver or external service is used by the calculation.

The report checks cover offline assets, section and reference integrity, default boundary behavior, every tagged displayed value and document rebuilding. Script behavior is checked with a simulated document, including distance selection and comment-file round trips. Browser execution is not part of this evidence: folder permissions and rendered chart behavior require an interactive review before general distribution.

Rebuild from the repository root using the command below. The module dependencies are Pydantic and the YAML reader; the surrounding environment supplies the package source path.

PYTHONPATH=src uv run --no-project --with pydantic --with pyyaml python docs/reports/modules/wfielddevelopment/build_report.py

The module report tests are located in tests/modules/field_development/test_module_report.py. The change record is changes.json, embedded below for offline viewing. Source-access records are provided in sources.json. Text files use UTF-8 encoding and line-feed line endings.
