1 Executive summary

The validation module is a schema and rule framework for screening energy records. Analysis is performed to determine the behaviour of its numeric range workflow; key results are summarized below.

  • The inclusive range workflow is available for bounded finite numeric records.
    • 4 of 6 public-example records are accepted by the module.
    • 1 acceptance differs from the public example at its exclusive upper limit; use of an inclusive limit is required for this workflow.
  • Use beyond this workflow requires a stated data contract.
    • Application checks are required for schema imports, null handling and cross-field execution before a dataset is accepted.
    • Engineering acceptance is NOT_EVALUATED; schema acceptance establishes only the checks actually executed.

2 Introduction

Record screening is performed before downstream energy analysis. Required fields, types, ranges, text patterns, dates and selected cross-field relationships are represented by schemas and rules [3].

The main workflow is demonstrated through the public record validator with explicit schema types. The public range example is used as a boundary comparison, with its exclusive upper bound preserved as the reference [1]. No physical structure, environmental load or engineering solver is represented.

3 Basis and criteria

The numeric example is taken from the public schema documentation [1]. The inclusion and exclusion criteria are defined by the validation specification draft [2]; the module is not presented as an implementation of that specification.

The reference lower bound is 0 and its exclusive upper bound is 100, both dimensionless. The same magnitudes are assigned to the module's inclusive bounds so that the semantic difference is exposed. The example is software data, with no physical operating limit inferred.

Each input and each expected reference outcome is recorded in the data register [3]. No fitted coefficient, material constant, engineering threshold or assumed physical value is used. A physical acceptance criterion remains NOT_EVALUATED until a cited application basis is supplied.

4 Inputs and outputs

Records are supplied as a dictionary, a list of dictionaries or a pandas data frame. A schema name, field definitions and optional cross-field rules are supplied to the record validator [3].

The return value is an acceptance flag and a list of validation exceptions. Non-strict mode accumulates errors; strict mode raises at the first encountered error. Field, value, rule and zero-based row position are available on the exceptions. A formatted text report is also available. Error counts are issue counts and are not generally rejected-record counts.

4.1 Compatible interface used here

The following imports select the same schema enumeration used by numeric dispatch. Field types from the alternate schema interface have matching labels but distinct identities; they are not treated as interchangeable.

from worldenergydata.validation import DataValidator
from worldenergydata.validation.schemas import DataType, FieldSchema, ValidationSchema

schema = ValidationSchema(name="NumericRangeExample")
schema.add_field(FieldSchema(
    name="value", data_type=DataType.FLOAT,
    required=True, nullable=False,
    min_value=lower_bound, max_value=upper_bound,
))
accepted, errors = DataValidator(schema, strict=False).validate(records)

The displayed bound symbols are supplied from the public example. The complete calculation is identified in the reference register [3].

4.2 Other output interface

Direct rule and predefined data-frame validators return a result object with errors, warnings, information and metadata. That interface differs from the record validator's tuple and exception interface. Its generic schema validate method returns an empty result; adding fields alone does not execute field checks through that method [3].

5 Theory and method

Range validation is performed by testing an inequality after field type checking. The finite numeric input is denoted x, the lower bound L and the upper bound U; all have the same units [2].

The inclusive condition is L ≤ x ≤ U. The public example uses L ≤ x < U. The lower inequality follows the minimum keyword; the upper inequalities follow maximum and exclusiveMaximum respectively [2]. No scaling factor or empirical equation is introduced.

Each published input is passed separately to the module. The complete set is also passed as a batch so that row positions and aggregated errors are recorded. Counts are formed from returned flags and exceptions; the disagreement percentage is the number of differing flags divided by the number of inputs, expressed as a percentage. Reference flags are taken from the published example, rather than calculated by a second call to the module [1, 3].

Cross-field checks are performed only when all field checks in the batch have produced no errors. An invalid field in any record therefore prevents cross-field checks for the entire batch [3].

7 Validation evidence

The repository's existing tests are used as evidence of checked software behaviour. The recorded focused execution passed 398 tests with 0 failures; the file-level counts and fingerprints are listed in the appendix [3].

Existing tests cover schema construction, exception context, result aggregation, required fields, type and range checks, text and date checks, cross-field relationships, file inputs and schema management. The public demonstration contains illustrative energy records; it is not a measured benchmark. No field-measurement acceptance benchmark is established by the inspected validation package, its focused tests or its demonstration [3].

Report tests compare every tagged worked-example number and the embedded chart data with fresh module calls. Separate literal anchors check the lower boundary, upper-bound discrepancy and total accepted and rejected counts. The headline accepted count is recomputed from the displayed inputs. Integer comparisons are exact; displayed percentages use a half-unit tolerance in the last displayed digit.

The generated report is compared with a fresh build using displayed precision. Calculation-source fingerprints detect a change requiring regeneration. These tests establish calculation consistency and the stated boundary cases; they do not establish general conformance or engineering acceptance.

8 Limits and recommendations

Use is limited to contracts whose checks have been exercised explicitly. The following controls are derived from the implementation and the public range criteria [2, 3].

8.1 Limits of use

The alternate schema enumeration can bypass numeric dispatch in the record validator. Numeric strings and booleans can pass its numeric type checks; nulls and non-finite values require caller checks. Range checks do not perform unit conversion. A missing required key can contribute multiple issues, and unknown cross-field rule types are silently ignored. Precision, scale, default values and named custom-validator declarations are stored without enforcement in the demonstrated record workflow.

Object-style cross-field rules in predefined data-frame schemas differ from the dictionary rules expected by the record validator. Several predefined column names and metadata field names also differ. File extension support does not establish data-contract compatibility; file workflows are not qualified by this example. Dataset values are logged by the existing validator, so logging configuration is part of application data handling.

8.2 Recommendations

  1. Use the demonstrated schema imports and add an application regression that rejects a value outside each supplied limit. Unify the schema enumeration before documenting the two interfaces as interchangeable [3].
  2. When the data contract has an exclusive bound, apply a separate strict inequality check before accepting the data. Trigger rejection at equality to the exclusive upper bound, as required by the public reference [2].
  3. Require finite numeric values and explicit units before range checking. Add regression cases for nulls, numeric strings and booleans before extending use to those input categories [3].
  4. Record whether cross-field checks actually executed, reject unknown rule types and qualify each predefined schema through its intended entry point before using it as an acceptance gate [3].
  5. Supply a cited dataset contract and measured reference records before using schema acceptance to support engineering acceptance. Keep the physical result NOT_EVALUATED until that basis is available.
