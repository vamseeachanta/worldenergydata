Why this replan exists

The 2026-07-16 plan must not be implemented. It would extend five files whose bytes are pinned by the v1 manifest while also requiring that v1 preflight to remain green. The live v1 manifest also records owner reuse as pending/false, the award locator collides on two Moho Nord rows, and the proposed v2 publication omitted the durable post-squash producer step.

This plan will preserve the Big Foot v1 pack byte-for-byte and build the portfolio contract in a v2 namespace. It will use the live baselines of 80 unique sanctioned projects and 110 awards across 29 projects. Counts will be recomputed at build time; they will not be treated as timeless constants.

2026-07-19 amendment checkpoint

This amendment will require a new user approval before implementation resumes. Review evidence records that locator hashes alone will not authenticate project/award source-row lineage across multiple corrections, inactive orphan crosswalk rows can bypass the identity ledger, and requirement foreign-key behavior must distinguish active closure from valid tombstoned history. The earlier approval does not enumerate the three additional provenance columns below, so review remediation will not be treated as authority to change the exact schema.

The amendment will add only old_source_row_sha256 and new_source_row_sha256 to identity migrations and created_locator_sha256 to requirement identities. It will also make complete crosswalk-to-identity closure mandatory for active and inactive project/award bindings; active subsets will remain separately equal. No allocation scenario, cost modeling, FX, workbook write, derived output, email, or external circulation will be authorized by this amendment.

Named-ref approval-history hydration

The validator will record ORIGINAL_HEAD, list origin refs, and select a ref whose advertised object equals that exact commit. Allowed namespaces will be refs/heads/*, refs/pull/<integer>/head, and refs/pull/<integer>/merge. For an attached checkout it will require the matching branch ref; for a detached checkout it will prefer exactly one matching pull ref, otherwise require exactly one matching branch ref. No match or multiple matches at the chosen priority will fail closed. It will fetch the selected name—not a raw SHA—into refs/codex/approval/1040-head, remove the shallow boundary for that named history, and then require the fetched ref to equal ORIGINAL_HEAD. A deleted, moved, or force-pushed ref between listing and fetch will therefore fail. It will separately fetch refs/pull/1052/head for the existing approval, refs/pull/1053/head for schema_amendment_approval, and refs/heads/main into dedicated trust refs. It will require reviewed commit 5ba42c1 under PR #1052, require the final reviewed amendment commit under PR #1053, require both published plans under trusted main and hydrated HEAD, verify exact old/new plan blobs plus the historical old marker blob, and validate the current amendment marker bytes/hash. A hostile node will prove that the two approval objects cannot swap refs, commits, or plan hashes.

Coverage formulas

Let P be the set of project summaries with requirements_derived; projects with requirements_unknown will be reported separately and excluded from, never silently added to, the requirement denominator. Let R be the set of active requirements belonging to P. Let A be the exact source-award-key set.

  • Requirement scope coverage: |{r in R: at least one confirmed link edge targets r}| / |R|.
  • Award resolution coverage: |{a in A: resolution(a)=linked}| / |A|; ambiguous and unlinked counts will be separate.
  • Disclosed-value coverage: |{r in R: a confirmed edge reaches an award with a numeric raw amount}| / |R|. not_public contributes scope evidence but not this numerator.
  • Arithmetic-eligible coverage: |{r in R: a confirmed edge reaches an arithmetic-eligible award}| / |R|. It is distinct from disclosed-value coverage and may legitimately be zero.
  • Each numerator is a set of requirement or award IDs, so bundles and multiple awards cannot double-count. If a denominator is zero, the serialized percentage will be null with denominator_zero, never zero or 100%. Every surface will persist numerator, denominator, unknown/excluded count, and exclusion reasons.

Stable source identity

Opaque project/award/source keys will be curated once and persisted; they will not be computed from row order or mutable locator content. The award crosswalk will bind each key to canonical JSON containing the exact five locator fields PROJECT, AWARD_YEAR, CONTRACTOR, ASSET_CLASS, and SCOPE_DESC; JSON encoding will use sorted keys, UTF-8, and no delimiter concatenation. That locator is unique for the current 110 rows. Later corrections will retain the key and opaque ID through the append-only migration ledger; deleted identities will be tombstoned and never reused. Tests will preserve existing Big Foot IDs and reject collisions, split/merge ambiguity, missing foreign keys, and key reuse.

Award linkage

Coarse ASSET_CLASS values will provide candidate lanes only; they will never confirm a link or scope coverage. A curated per-award scope edge must cite the exact source scope before a requirement link becomes confirmed. Otherwise the award will remain explicitly ambiguous or unlinked. Negative tests will cover live counterexamples: an sps riser-only award, an other drilling award, an other export award, and an installation award bundling SURF/control scope. Bundled scope will link once to multiple requirements through one award ID and one bundle group; value will never be copied.

For each award, let S be its curated source-scope-component set and C the components with at least one confirmed requirement edge. Scope coverage will be full when |S|>0 and C=S; partial when 0<|C|<|S|; none when |C|=0 and every component is rejected; and unknown when any unresolved component is ambiguous and no component is confirmed. Link-resolution precedence will be: ambiguous if project resolution or any source component is ambiguous; otherwise linked if at least one edge is confirmed; otherwise unlinked. Counting disposition will come only from the curated counting-decision row and may remain unknown.

Accounting normalization

The raw v2 accounting model will remain separate from the v1 MoneyInterval. Every row will preserve VALUE_LOW_MM, VALUE_HIGH_MM, and the original eight-value VALUE_BASIS. Amount availability will be none|low_only|high_only|both_equal|both_unequal; a representable raw bound shape will be point|floor|ceiling|closed_range, otherwise invalid. This source has no endpoint-inclusivity field, so raw v2 will not claim open_range. Rows with no amount will carry no interval. An eligible v1-compatible MoneyInterval may be created only after all required accounting facts and source-basis compatibility pass.
