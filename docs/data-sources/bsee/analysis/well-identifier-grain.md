## Decision and identifier definitions

Grain and duration basis are separate attributes. A bore count is not a well-family count; a sum of bore days is not a family interval union or a calendar span. Existing published numbers are unchanged. The metric inventory below states the aggregation actually performed by the checked-in builders, including where a generic input does not establish an identifier grain.

| Identifier | Meaning supported by reopened sources | Use in this record |
|---|---|---|
| API-10 | State/pseudo-state (2 digits), county/pseudo-county (3), unique well sequence (5), from R1, attachment pages 2-3. A well can contain multiple wellbores. | Well family: first ten characters of the normalized bore identifier. |
| API-12 | API-10 plus a two-digit wellbore (WB) code. Original hole uses `00`; subsequent numbered sidetracks and bypasses share a sequence (R1, attachment page 3). | Bore, not completion. A nonzero suffix alone does not identify a geologic sidetrack. |
| API-14 | Primary-source definition **not verified**. The research note describes a vendor event sequence after API-12, based only on secondary R9; see Not verified. | No established BSEE completion join key. No metric is reclassified as completion-grain from this label. |
| Completion key | API-12 plus a separate three-character `PROD_INTERVAL_CD`; monthly production also needs reporting month/context (R1, attachment pages 4-5; R4; R7 fields 13-14). | Completion production, distinct from bore rig time. `X01` denotes wellbore-only reporting in R1. |

Table 1. Identifier meanings and intended counting units.

R1 assigns WB codes to sidetracks regardless of production and to qualifying bypasses. A bypass shorter than 100 ft with neither geological data nor a directional survey receives no new API number. Deepening to the original target retains the identifier. Later work in the same bore therefore does not necessarily create a new API-12; a subsequent numbered sidetrack does. A new reservoir completion in that bore changes the interval number, not the API-10 family (R1, attachment pages 3-4).

`WELL_NM_ST_SFIX` counts changes to a geologic objective; `WELL_NM_BP_SFIX` counts redrilling toward the same objective (R3, R6). `WELL_NAME_SUFFIX` records additional bore drilling (R2). These suffixes describe a different sequence from WB. The research note's proposed WB-to-ST/BP mapping is an inference, not a verified mapping of the actual families.

## Tables, loaders and family keys

R2 and R3 define `API_WELL_NUMBER` using the component structure above but declare `VARCHAR2`, field length 36. This is schema capacity, **not evidence that stored values are always twelve characters**. R4 explicitly fixes the OGOR-A API field at length 12, start position 50, and the interval at length 3. The ONRR handbook separately requests a twelve-character API and a three-character producing interval (R7, chapter 5, OGOR-A fields 13-14).

### Code versus documentation

- The frozen [per-well listing:11](../../../../reports/lower_tertiary/wo-april-2026-per-well-dc.md#L11) describes drilling as spud-to-TD and completion as post-TD servicing. Today's extractor instead selects WAR activity codes. Its newer code cannot establish the basis of an older published number; regeneration is separate work.
- That listing's [suffix label:13](../../../../reports/lower_tertiary/wo-april-2026-per-well-dc.md#L13) and [builder flag:156](../../../../scripts/lower_tertiary/build_wo_per_well_dc.py#L156) call every nonzero suffix a sidetrack. R1 includes bypasses in WB numbering. These are non-original bores, not a verified sidetrack-only population.
- Benchmark “Drill days” and “Compl days” are calendar intervals despite similar names on rig-day surfaces. The [facts builder:23](../../../../scripts/lower_tertiary/build_wells_facts.py#L23) already records the distinction.
- The [historical summary:30](rig_days/rig_days_summary.md#L30) lists competing completion formulas and asks for a decision. It is not evidence of an adopted current family-span rule.

## Proposed, not implemented

The research note proposes **API-12 bore x contiguous activity episode**, carrying `api10` for roll-up; counts would state bores versus families, and production would retain the completion interval and month. Borehole/WAR joins would normalize twelve-character keys and reconcile renumbering through `PREV_API_NUMBER` (R5); `SN_WAR` and report bounds would identify, order and de-overlap activity records. These normalization/renumbering/episode requirements are not established by the current string normalizer.

Its proposed replacement for the date hull would calculate days per bore and sum within a family only after confirming bore-specific spud dates. If spud repeats the original well date, the proposal would investigate a bore-specific kickoff, previous-bore TD or first WAR date as the start, without spanning idle gaps. These alternatives are **not verified equivalent start dates** and are not adopted here. Re-entry episodes would remain attached to the same bore unless a new numbered bore is created; rig time would not be multiplied across completion intervals.

Current `rig_days_by_well` already unions the family's WAR intervals and emits additive columns separately. That implementation addresses overlap at bore transitions; it is **not** the research note's conditional sum of per-bore milestone differences. Episode partitioning, renumbering and any change to retained metadata need their own reviewed implementation and declared acceptance rule.

## Not verified

- API Bulletin D12A and the full PPDM standard were not opened here. R8 verifies custody/successor status only. API-14 as a vendor event sequence is the research note's **secondary-only** description (R9), not a verified primary standard or a BSEE completion identifier.
- Stored length/format across the full borehole, WAR and OGOR-A feeds was not profiled. The committed population check establishes twelve digits only for its extracted CSV.
- Repeated original spud dates on sidetracks, actual WB-to-ST/BP mappings within families, and a field-definition page for the completion table itself remain unverified. OGOR-A and the handbook are supporting production evidence, not that missing table definition.
- R1's cover prints an expiration date of 2014-11-03; R1a still displays Active. Formal reissue/current legal status beyond those observations is not established. R1 is used for the documented numbering scheme, not a current compliance opinion.
- The memberships behind 184 and 211, live external publication parity, and complete raw-data recomputation are not established. No private datasets or licensed software were used.
