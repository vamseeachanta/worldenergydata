Production-reservoir database

The offline SQLite store connects explicit regulator identities, field/facility/reservoir catalog entries, monthly production snapshots and retained decline parameters. Source vintages remain separate. No regulator observations are bundled; engineering suitability is NOT_EVALUATED. Scope: issue 680.

Scope and API

The implementation is worldenergydata.production.database in the production distribution. The reservoir estimation distribution remains independent. All database paths are caller supplied. Opening a store uses SQLite and performs no network retrieval.

  1. Catalog: add_asset stores fields, facilities, reservoirs and aggregates; link_asset supports shared facilities and reservoirs; map_field records exact, source-scoped external identifiers.
  2. Production: add_snapshot records a source version, original SHA-256, locator, timezone-qualified retrieval time and reported/synthetic classification. ingest atomically seals a complete normalized batch. source_snapshot, production and linked_assets provide readback.
  3. Decline: decline_history returns contiguous, positive oil volumes for the existing monthly fitter. save_decline retains supplied parameters against a recomputed input digest; decline_curve returns provenance and qualification.

The adapter's field_name token is mapped exactly. Names are not globally unique identifiers. The caller must distinguish ambiguous names before ingest and justify any cross-regulator equivalence. No fuzzy matching or automatic cross-regulator aggregation occurs. Aggregate series cannot supply field decline histories.

Inputs, units and unknowns

Ingest accepts mappings with the existing unified.query.STANDARD_COLUMNS keys: region, field_name, year, month, oil_bbl, gas_mcf, water_bbl, condensate_bbl, source. Rows may come from adapter.fetch(query).to_dict(orient="records") after explicit upstream unit normalization. For a frame containing missing values, use frame.astype(object).where(frame.notna(), None) before conversion to records.

The complete CANONICAL_UNITS mapping is required at ingest. Negative values, booleans, NaN, infinity, invalid calendar periods, absent mappings and duplicate asset-month records reject the entire batch. A genuine zero is retained. A failed batch remains retryable; a successfully loaded snapshot is immutable. Empty snapshots are rejected. New source releases require new snapshot IDs. Multiple source reports are queried separately and are never added together implicitly. Corrections with negative signed volumes require explicit upstream treatment.

Decline method and evidence

The existing fitter uses month=1,2,... and rate_bbl in bbl/month. The bridge preserves that convention; it performs no daily-rate conversion. Missing calendar months, absent oil values, zero oil values and aggregate assets reject decline preparation. The stored origin_period is the first observed period, corresponding to index 1; the initial parameter qi is the model's extrapolated value at index 0. Synthetic snapshots require allow_synthetic=True and retain their classification in stored curves. Recognizable mock or synthetic adapter labels cannot enter a reported snapshot.

EIA, Production Decline Curve Analysis in the Annual Energy Outlook, released 2023-03-16, gives the hyperbolic equation q(t)=qi/(1+b Di t)^(1/b). The exponential limit is q(t)=qi exp(-Di t), and substitution of b=1 gives the harmonic form. The source page and its equation image were retrieved successfully on 2026-10-20. These equations describe the existing fitter's parameter convention; the database implements storage and input preparation, not another optimizer.

The cited EIA study also describes first-month exclusion, normalization and a terminal decline switch. None of those EIA workflow choices is imposed by this database. Economic limits, fit quality criteria, producing-time corrections and reservoir applicability require separate evidence. Stored parameters are always NOT_EVALUATED for engineering use. EUR and reserves classification are not stored or qualified.

Worked example

examples/production_database.py retains an invented raw JSON sequence, its digest, a SQLite store and a read-back manifest. The source uses reserved example metadata and is explicitly synthetic. Run from an environment containing the production package:

python examples/production_database.py --output-dir <new-output-directory>

Inputs are 100, 80 and 64 bbl in consecutive months, with unknown gas and measured zero water. Hand addition gives 244.0 bbl. Consecutive ratios are 0.8; with the fitter's one-based index, qi=125 and Di=ln(1.25) give 125(0.8)^1=100, 125(0.8)^2=80 and 125(0.8)^3=64. These values are invented arithmetic inputs, not sourced production measurements. The example passes an explicit demonstration economic cutoff and output horizon to the existing fitter; it does not use its EUR. Readback yields 244.0 bbl total, 125.0 bbl/month fitted initial parameter, synthetic classification and NOT_EVALUATED status.

Verification and remaining scope

The new tests cover all seven source IDs, persisted readback, shared facility/reservoir links, calendar rollover, explicit units, atomic rollback, duplicate rejection, SQL parameter binding, separate vintages, mock classification, history digests and the independent arithmetic above. The worked-example test exercises the existing fitter and checks retained raw-source bytes.

Live collections, raw regulator schema parsing, unit conversions, verified source rights and freshness, independently reviewed identity crosswalks, reservoir property measurements, migrations from existing databases and engineering qualification remain outside this initial database. The existing adapters and upstream source maintainers retain those responsibilities. Continued work remains tracked by issue 680.
